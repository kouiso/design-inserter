# OpenSpec — AI エージェント向け仕様管理ルール

作成日: 2026-05-03

---

## 目的

OpenSpec は AI エージェント（Claude, Codex, Cursor 等）が**仕様駆動で開発を行う**ためのフレームワークである。

- 仕様ファイル（spec）を Single Source of Truth として扱う
- 実装前に必ず spec を読み、spec に書かれていないことは実装しない
- spec の変更は提案→実装→検証のワークフローに従う

---

## ディレクトリ構成

```
openspec/
  AGENTS.md          ← 本ファイル（AI向けルール）
  project.md         ← プロジェクト全体のコンテキスト
  specs/
    gutenberg-block.md
    shortcode.md
    catalog.md
    scraper.md
    rendering.md
    editor-ui.md
```

---

## Spec ファイルのフォーマット

各 spec ファイルは以下のセクションを**この順序で**含む:

```markdown
# タイトル

作成日: YYYY-MM-DD

## 概要
1-3 文で spec の対象と目的を説明する。

## 機能要件
番号付きリストで、実装すべき振る舞いを列挙する。

## 非機能要件
パフォーマンス、セキュリティ、互換性、保守性に関する制約。

## データ構造
JSON schema、型定義、DB テーブル定義など。コードブロックで記述する。

## エッジケース
| ケース | 期待される振る舞い | 備考 |
|--------|-------------------|------|
| ...    | ...               | ...  |

## 受け入れ基準
- [ ] チェックボックス形式で検証可能な条件を列挙する
- [ ] 各項目は「〜であること」の形式で記述する

## 関連spec
- [spec名](相対パス) — 関連の説明
```

## AI エージェントの行動ルール

### 実装前

1. 対象機能の spec を**全文**読む
2. 関連 spec も読み、依存関係を把握する
3. spec に記載されていない要件は実装しない
4. spec の内容に疑問がある場合はユーザーに確認する

### 実装中

1. spec の機能要件を 1 つずつ実装する
2. エッジケース表の全行を考慮する
3. 非機能要件に違反しないことを確認する
4. spec に記載のないリファクタリングや「改善」を勝手に行わない

### 実装後

1. 受け入れ基準の全チェックボックスを検証する
2. 未達成の基準がある場合は完了報告しない
3. spec と実装の乖離を発見した場合は報告する

---

## 変更管理ワークフロー

### 1. 提案（Proposal）

spec の変更が必要な場合:

- 変更理由を明示する
- 影響を受ける関連 spec を列挙する
- ユーザーの承認を得てから spec を更新する

### 2. 実装（Implementation）

- 承認された spec に基づいて実装する
- spec と実装を同一 commit に含めることを推奨する

### 3. 検証（Verification）

- 受け入れ基準を全て満たすことを確認する
- 関連 spec への影響がないことを確認する

---

## 禁止事項

1. **spec を読まずに実装を開始する** — 仕様の見落としが発生する
2. **spec に書かれていない機能を追加する** — スコープクリープの原因
3. **spec を暗黙に変更する** — 提案ワークフローを経由すること
4. **受け入れ基準を省略する** — 検証不能な仕様は仕様ではない
5. **「明らかだから」と spec 記載を省く** — AI は文脈を忘れる

---

## Spec の粒度ガイドライン

| 粒度 | 例 | 推奨 |
|------|-----|------|
| 大きすぎる | 「プラグイン全体」 | 分割する |
| 適切 | 「Gutenberg ブロック」「レンダリング」 | この粒度で書く |
| 小さすぎる | 「SelectControl の onChange」 | 上位 spec に含める |

1 つの spec ファイルは 80-150 行を目安とする。それを超える場合は分割を検討する。

---

## Spec 間の参照ルール

- 相対パスで参照する: `[catalog](specs/catalog.md)`
- 循環参照は許容するが、主従関係を明記する
- 関連 spec セクションには双方向リンクを記載する

---

## バージョニング

- spec は Git で管理する
- 大きな変更には commit message に `spec:` prefix を付ける
- 実装と spec の変更は同一 PR に含めることを推奨する
